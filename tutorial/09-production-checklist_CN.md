# 9. 上线之前

中文 | [English](09-production-checklist.md) · [教程目录](README_CN.md)

一份检查清单。每一条都附带理由，因为说不出理由的条目，你迟早会跳过。

## 环境变量

**`NODE_ENV=production`** —— 这一个设置改变两处行为：错误响应不再带堆栈，
`/health/ready` 不再带检查的 `details` 与错误字符串。这两个都是免认证的暴露面，
否则它们会把主机名、端口、数据库名交出去。

**`LOG_LEVEL`** 设为 `info` 或 `warn`。debug 级别会把执行过的每条语句都记下来。

**`KEELSON_LOG_SQL_PARAMS` 不要设。** 设成 `true` 会把绑定参数值——口令、token、
个人数据——打进日志。它是为某个糟糕的下午准备的，不是常态。

**`Controller.debugEnabled` 为 false**（默认值）。为 true 时会打印 `req.body` 与
`req.query`，也就是客户端发来的一切。

## 网关之后

如果你用的是默认的 `HeaderUserResolver`，`user` 头就是调用者的身份，并且被完全信任。
请核实两件事：

- 服务除了经由网关之外不可达——没有第二条 ingress，没有调试端口，集群内部也访问不到
- 网关在设置自己的 `user` 头之前，**剥掉**客户端带来的同名头

任何一条不确定，就换一个验签的解析器（第 5 章）。这是这份清单上后果最严重的一条：
弄错了，任何调用方都可以是任何用户。

## 数据库

**连接池大小**是想过之后定的。多数驱动默认是 10；合适的数字通常由数据库的
`max_connections` 除以 pod 数量决定，而不是由单个 pod 想要多少决定。

**`REQUIRES_NEW` 都审过。** 每一个都会在外层事务占着第一个连接时，再从池里取第二个。
放在循环里，这就是连接池死锁的造法。

**长事务看过。** 一个在 `@Transaction()` 里调 HTTP 接口的方法，会在整个调用期间占着
连接。把网络调用挪到事务边界之外。

**非数据库的操作挪出去了。** 发邮件、投消息、写缓存都不会回滚。做法见第 2 章。

## 关停

**处理了 `SIGTERM`** 并接到 `shutdown()` 上。没有它，pod 终止会打断在途请求和
处理到一半的批次。

**`terminationGracePeriodSeconds`** 比"最慢的请求 + 最慢的 `processItem`"更长。
短了，编排器会在你关停的中途 `SIGKILL`。

**处理器是幂等的。** 关停会等待在途条目，但 `SIGKILL`、OOM kill、节点宕机不会等。
`loadToProcessData()` 所依据的查询条件，必须在一次粗暴重启之后依然能选中那条数据。

## 健康探针

**存活与就绪指向了正确的端点。** 存活用 `/health/live`，就绪用 `/health/ready`。
把存活指向就绪，意味着数据库抖一下就会让所有 pod 同时重启，把一次短暂故障变成雪崩。

**依赖分了类。** 关键的意思是"请求会失败"——通常是数据库。非关键的意思是
"请求会变慢"——比如缓存。关键检查 DOWN 会把 pod 移出负载均衡；非关键的只报 DEGRADED
并继续服务。

**检查超时设得比探针自己的超时更短。** 检查默认 3 秒。如果探针超时是 2 秒，
探针会先于检查放弃，你什么也没学到。

## 日志

**装了实现**，或者明确决定就用 console 回退。回退是往 stdout 写纯文本；
如果你的采集端期待 JSON，就装 `@ticatec/logger-pino` 并在任何东西打日志之前调
`initialize()`。

**异常以异常的形式传入**——`logger.error(err, 'message')`，绝不是
`logger.error({ err }, 'message')`。后者会丢掉 message 与 stack。

**category 调过。** `dao` 与 `db` 设成 `warn`，既挡住了逐条语句的日志，
又让 `service` 保持有信息量。

## 构建与依赖

**自己的 tsconfig 开了 `strict`。** 每个 Keelson 包都是在 strict 下构建的；
你消费到的类型，只能在你自己的设置允许的范围内发挥作用。

**`reflect-metadata` 只导入一次**，在入口文件的最前面。

**对等依赖锁在你测试过的范围内。** Keelson 声明得很宽——`>=1.0.0`——因为它不知道你的
组合。你的 lockfile 应该知道。

**一个进程一种模块格式。** 同一个包的 CJS 与 ESM 两份同时被加载是能工作的——
单例锚定在 `globalThis` 上正是为了这个——但代码会被加载两遍。如果启动内存偏高，
去查一下你的打包结果。

## 第一次部署之前

- 跑一遍 `pnpm verify`——构建、类型检查、测试，按这个顺序
- 在本地用 `NODE_ENV=production` 启动，把开头五十行日志读一遍。
  漏装实现、category 配错、密钥泄漏，都在那里现形
- `curl /health/ready`，确认响应体里没有 `details`
- 故意制造一个 500，确认响应里没有堆栈
- 从网关外面发一个伪造 `user` 头的请求，确认它到不了你这里

最后这条值得手动做一次，从集群外部。它检验的是第 5 章那个前提在你的部署里到底成不成立。
